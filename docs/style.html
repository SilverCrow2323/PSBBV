07 / Editorial identity

NO GREY WALLS. NO EMPTY HYPE.

Documentation is part of the product. Every guide should be useful, visually alive, easy to scan and honest about what the software can actually do.

The one rule

Make it clear. Make it good. Make it ours. A reader should never have to fight a page to find the answer—and should never mistake a concept for a working feature.

Two visual systems / one identity

Related, not interchangeable.

The Vita interface and the documentation site have different jobs. They share a family resemblance, not the same paint bucket.

Voice & tone

Talk like a person who knows the system.

Direct, accessible, slightly cheeky. Never pompous, never cryptic, never rude to the person reading.

✓

Say this

“The app checks the file and shows an error if it cannot read it.”

“This part is not ready yet.”

“Press Circle to go back.”

×

Not this

“The application undertakes a comprehensive validation procedure.”

“This functionality is expected to be made available in a future iteration.”

“Utilize the circular input modality.”

Page anatomy

Different pages. Different rhythm.

Variety matters. A troubleshooting guide should not look like a product pitch wearing a fake moustache.

▤

Quick facts & tables

Put versions, platform, requirements and comparisons where readers can find them immediately.

▧

Cards & callouts

Group related choices, warnings, shortcuts and important limitations. Keep them purposeful.

⌘

Diagrams & artwork

Use original SVGs, screenshots of real behavior and diagrams to explain relationships—not to fake progress.

Status language / no wishful thinking

Labels mean something.

LabelMeaning
🟢 READYImplemented and verified for the stated environment.
🟡 IN PROGRESSImplementation has started; known gaps remain.
🔵 PLANNEDDesigned or discussed, not implemented.
🟠 NEEDS TESTINGBuilt, but not yet verified on target hardware.
🔴 BLOCKEDCannot proceed until a named issue is resolved.
⚠
A green CI run is not a hardware certificate.

Always name the environment and test scope. Cross-compilation, packaging, emulator checks and physical Vita validation are separate gates. No badge gets to blur that line.

Before a page ships

The SPDW pre-flight.

  1. Are the commands and links current?
  2. Is every described feature actually implemented?
  3. Are prerequisites, tested versions and limitations visible?
  4. Can a reader follow the steps without guessing?
  5. Does the page use a visual structure that fits its content?
  6. Does it sound and feel like SPDW Factory?
